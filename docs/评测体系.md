# 评测体系设计说明

这份文档回答一个问题：**这套评测的每一处设计，依据是什么。**

---

## 一、出发点：不抄榜单

大多数"大模型评测"的做法是：找几个公开榜单，跑一遍，排名。
这条路有三个绕不开的问题：

1. **饱和快。** 公开基准一旦发布，厂商就会针对性优化，区分度在几个月内掉光。
   SWE-bench Verified 已经出现饱和迹象，不得不推出更难的 Pro 版本。
2. **与真实使用脱节。** 考研题得分高，不代表能处理用户手里那个 messy 的真实请求。
3. **不可解释。** 榜单只给一个总分，不告诉你差在哪、下一步补什么。

所以本框架采用另一条路：**先梳理真实用例，再抽象成可评测的类别。**

这也是 Seed 的做法。Seed1.8 模型卡里写得很直白：

> benchmark scores must serve as a reliable proxy for actual value
> （评测分数必须是真实价值的可靠代理）

## 二、对齐的参照：Seed 的评测方法学

### 2.1 三原则（Seed1.8 Model Card 附录 A）

| 原则 | 含义 | 在本框架里的体现 |
|---|---|---|
| 优先用户体验 | 先分析真实用例分布，再把用例映射成 benchmark 类别 | 8 个维度全部标注了真实用例来源 |
| 转向真实场景 | 从合成孤立任务，转向按经济价值领域组织的真实任务 | `realworld` 维度：行程规划、政策遵循、决策取舍、预算分配 |
| 推进智能前沿 | 另设高阶推理/代码评测，测峰值能力 | `reasoning` / `coding` 维度保留高难度题 |

### 2.2 产品驱动评测（Seed2.1 Model Card）

Seed2.1 的做法更贴近工程实践：

1. 靠内测（dogfooding）+ 外部测试者 + 众测持续迭代
2. **从用户返回的真实 badcase 持续扩展 benchmark**；大规模访谈把"未满足需求"转成评测任务
3. 用模型自己参与迭代：评测构建、失败分析、数据清洗、数据合成

第 2 条是本框架 `analysis.py` 的设计依据 —— **badcase 不是终点，是下一轮数据生产的起点。**

### 2.3 四维框架与两个短板（Seed2.0 Model Card）

Seed2.0 明确点名要补的两个短板，以及它的四维评测框架，直接决定了本框架的维度划分：

- 短板一：**长尾知识缺口** → `knowledge`
- 短板二：**复杂多步指令失败** → `instruction`
- 四维：**科学发现 / Vibe Coding / 上下文学习 / 真实世界任务**
  → `coding` / `long_context` / `realworld`（科学发现合并进 `reasoning` 的高难度部分）

### 2.4 Agent 评测的参照：τ-bench 与 GAIA

- **GAIA**：真实世界多步任务，有确定性答案，分三级难度
- **τ-bench**：引入 **pass^k** —— 同一题跑 k 次全通过才算过。
  实验结果：SOTA 工具调用 agent 单次成功率约 50%，但 **pass^8 掉到 25% 以下**

后者直接决定了 `agent` 维度必须设 `repeats: 3`。只看单次成功率会系统性高估可用性。

## 三、十个能力维度

| 维度 | 测什么 | 判定方式 | 主要指标 |
|---|---|---|---|
| `knowledge` | 事实性、长尾知识 | 规则（mcq）+ 参考对齐裁判 | 准确率、事实一致率 |
| `instruction` | 格式/长度/必含/禁含/否定约束 | **以规则为主**，裁判补充语义层 | 约束满足率、硬违规数 |
| `reasoning` | 数学、逻辑、多步推理 | 数值容差 + 裁判 | 准确率 |
| `coding` | 代码正确性、边界处理 | 裁判（可扩展到执行测试） | 质量分 |
| `long_context` | 长材料中提取并推理 | 参考对齐裁判 | 事实一致率 |
| `knowledge_graph` | 三元组抽取、关系方向、多跳推理 | **规则为主**（F1）+ 裁判兜底 | 三元组 P/R/F1、路径命中率 |
| `agent` | 工具选择、参数、轨迹、可靠性 | 轨迹判定 + 任务完成 | 工具 F1、**pass^k**、步数 |
| `multi_agent` | 分工是否成立、制衡是否有效 | **全确定性** + 裁判兜底 | 角色覆盖、审查履职率、修订闭环率 |
| `realworld` | 端到端任务完成 | 多维加权裁判 | 质量分 |
| `safety` | 拒答边界、幻觉、提示注入 | 规则启发 + 裁判 | 拒答正确率、注入抵抗率 |

**为什么 `instruction` 要特别强调规则判定**：字数超没超、有没有出现禁用词，
这些是确定性问题。用 LLM 去判它，既贵又不稳定，而且引入完全不必要的偏差。

**为什么 `knowledge_graph` 也以规则为主**：三元组抽取的对错可以逐条比对
（主语、关系、宾语三者都对才算命中），这种判定交给裁判反而是倒退。

**为什么 `multi_agent` 几乎全是确定性判定**：协作的失效模式都很具体 ——
审查者有没有否决过、否决之后有没有改、某个角色是不是包办了所有消息。
这些都是可以在消息记录上直接数出来的事实，不需要主观判断。

## 四、评分表（Rubric）怎么设计

参考 G-Eval（Liu et al., 2023, arXiv:2303.16634）。一张合格的评分表有四个必需件：

### 4.1 显式 criterion

不是"评价这个回答好不好"，而是把标准写成可执行的一段话。

反例：
> 请给这个回答打分（1-10 分）。

正例（`faithfulness.yaml`）：
> 逐条检验回答中的事实性陈述是否成立。判定依据的优先级：给定材料 > 公认事实。
> 严禁因回答冗长、语气自信、排版精美而提高分数。

### 4.2 有序的 evaluation_steps

```
1. 抽取回答中所有可独立判定的原子事实陈述
2. 对每条陈述标注 SUPPORTED / CONTRADICTED / NOT_IN_REFERENCE
3. 计算 unsupported = CONTRADICTED + NOT_IN_REFERENCE 的数量
4. 依据 unsupported 的数量与严重程度，映射到 anchors 中的某一档
5. 先写出逐条判定与计数，最后才给最终分数
```

**"先推理，后打分"是硬性要求。** 先给分数再补理由，那个理由只是分数的装饰品。
2026 年的 "Judging the Judges" 基准测试了九种策略，CoT 单独带来 +7.2 分的一致率提升。

### 4.3 带锚点的分数刻度

裸 1-5 分在不同 prompt 之间不可比。必须有文字锚点：

```yaml
5: 全部事实性陈述均被给定材料或公认事实支持，无编造
4: 仅一处轻微过度概括，不影响结论成立
3: 存在 2-3 处无依据陈述，或 1 处与给定材料直接矛盾
2: 存在多处编造或矛盾，答案主体不可信
1: 大部分内容为编造，或与给定材料严重冲突
```

### 4.4 严格的 JSON 输出契约

自由文本没法做统计。裁判必须返回结构化 JSON。
**解析失败时按"判定作废"处理，绝不默认给分** —— 静默兜底会把错误的分混进统计里。

### 4.5 多维拆分的意义

`helpfulness.yaml` 把"好不好"拆成四个可分离的子维度并加权：

| 子维度 | 权重 | 含义 |
|---|---|---|
| correctness | 0.40 | 结论与推导是否正确 |
| completeness | 0.25 | 是否覆盖全部要点 |
| relevance | 0.20 | 是否在回答真正的问题 |
| clarity | 0.15 | 是否易于阅读 |

拆维度的价值在**可审阅**：
「3.2 分，因为正确性 3 分而完整性只有 2 分」比「3.2 分，感觉一般」有用得多。

## 五、指标口径

### 5.1 分数与通过

| 概念 | 口径 | 定义位置 |
|---|---|---|
| **综合分** | 有裁判分用裁判分，否则用确定性判定均值 | `analysis.final_score` |
| **通过** | 所有给出明确结论的判定都通过才算通过 | `analysis.is_pass` |

综合分的口径刻意定得很明确：**两条路径不混着平均**。
把规则分和裁判分平均，会让"格式合规"这种确定性结论稀释掉质量信号。

通过口径也刻意设得很严：**一处硬约束不合规就是不合规**，评测不发安慰奖。

### 5.2 置信区间

所有均值都配自助法（bootstrap）95% 置信区间，1000 次重采样。

为什么必须给：两个模型均分 3.82 和 3.79，没有区间你会以为前者更强；
有了区间你可能会发现两者完全重叠 —— 那这个差距根本不存在。

### 5.3 Agent 专属指标

| 指标 | 定义 | 为什么重要 |
|---|---|---|
| `tool_precision` / `tool_recall` / `tool_f1` | 实际工具序列与期望序列的匹配度 | 只看结果会奖励"歪打正着" |
| `redundant_steps` | 超出期望次数的重复调用 | 冗余步骤直接对应成本 |
| `missing_tools` | 期望调用但未调用的工具 | 定位是漏了哪一步 |
| `safety_violation` | 是否调用了禁用工具（布尔） | 比答错更严重，单独出指标 |
| **`pass@k`** | 跑 k 次至少成功一次 | 能力上限 |
| **`pass^k`** | 跑 k 次全部成功 | **可靠性，上线决策该看的数** |

`pass@k` 与 `pass^k` 差距越大，模型越不稳定 ——
这类模型上线风险最高，优先要解决的是稳定性，而不是把平均分再抬高一点。

## 六、三层判定架构

```
Tier 1  确定性规则
        全量执行 · 零成本 · 零延迟 · 零偏差 · 完全可复现
        ├ 约束类：must_contain / must_not_contain / max_chars / exact_lines
        │         json_schema / regex_fullmatch / language / no_preamble
        ├ 比对类：mcq 选项 / 数值容差 / 精确匹配 / bigram F1
        └ 安全类：拒答特征 / 危险指令模式

Tier 2  LLM 裁判
        抽样执行（judge_sample_ratio，生产建议 0.1-0.2）
        ├ G-Eval     单点打分
        ├ Pairwise   双向换位对比
        └ Reference  参考对齐（忠实度、正确性）

Tier 3  人工标注
        小样本（建议 100-500 条），只用来校准 Tier 2，不用来打分
```

这个分层对应三层成本策略：**裁判做量，人只做校准。**
没有人的校准，裁判的分就是个装饰性数字。

## 七、裁判校准

### 7.1 为什么用 κ 而不是一致率

原始一致率会被"多数类"灌水。两个都爱打 5 分的裁判，一致率天然很高，但毫无信息量。
Cohen's κ 扣掉了随机一致的那部分，所以它才是能拿去决策的数。

### 7.2 用哪种 κ

| 数据类型 | 用什么 | 理由 |
|---|---|---|
| 二分类（pass/fail） | 未加权 Cohen's κ | 无有序关系 |
| 有序评分（1-5） | **二次加权 κ** | "把 3 打成 5"和"把 3 打成 4"的错误程度不同，未加权会把两者一视同仁 |

### 7.3 判读区间

Landis & Koch (1977) 的惯例（是惯例，不是物理常数）：

| κ | 一致性 |
|---|---|
| < 0.00 | 低于随机水平 |
| 0.00-0.20 | 极弱 |
| 0.21-0.40 | 一般 |
| 0.41-0.60 | 中等 |
| **0.61-0.80** | **强 ← 生产警戒线通常取 0.6** |
| 0.81-1.00 | 几乎完全一致 |

另一条实践共识：裁判与专家一致率达到 **85%-90%**，才适合用作发布门禁。

本框架的行为：`κ < 0.6` 时，报告明确标注"分数只能作参考，不应作为发布门禁依据"，
而不是悄悄给一个看起来很正常的小数。

### 7.4 校准流程

```bash
# 1. 采一批样本，人工按同一张评分表打分，存成 JSONL
#    格式：{"sample_id":"kn-001","sut_id":"deepseek-chat","score":4,"notes":"..."}
# 2. 跑评测
python run.py run --suite all
# 3. 算一致性
python run.py calibrate --run latest --gold datasets/calibration/gold_helpfulness.jsonl
```

**重要**：校准不是一次性的。换裁判、换被测模型、换评分表、或者过了 60-90 天，
都必须重新校准 —— 服务商会在你脚下悄悄更新模型。

### 7.5 评审团一致性（多裁判时才有）

当配置了多个裁判（评审团）时，除了「裁判 vs 人工」的一致性，还要看**裁判之间**的一致性。

这两件事问的不是同一个问题：

| 度量 | 回答的问题 | 低值意味着 |
|---|---|---|
| 裁判 vs 人工 κ | 裁判的分能不能信 | 评分表有歧义，或裁判不行 |
| 裁判之间 κ | 评审团有没有增加信息量 | 要么评分表有歧义，要么几个裁判高度同质 |

判读方式：

| 评审团 κ | 结论 |
|---|---|
| 接近 1 | **要反过来警惕**：几个裁判几乎从不分歧，说明评审团没有比单裁判多提供信息 |
| 0.5 – 0.8 | 健康区间：方向一致，但各自保留独立判断 |
| < 0.5 | 评分表本身有歧义。**该回去改标准，而不是再加裁判** |

### 7.6 评审团怎么聚合：中位数，不是均值

```
同一指标下的多个裁判分 → 取中位数 → 再跨指标平均
```

用中位数而不是均值的理由只有一个：**评审团的意义在于抗离群**。
三个裁判给 [5, 5, 1]，均值是 3.67，中位数是 5 —— 前者让一个抽风的裁判带走了整体分数。

另外，各裁判**独立打分，不共享上下文**。一旦某个裁判能看到别人的结论，
它就不再是独立样本了，「用不同偏差互相抵消」这个机制会失效，只会放大最先开口那个模型的偏好。

## 八、偏差控制

裁判不是中立仪器。四类已知偏差与对应手段：

| 偏差 | 表现 | 本框架的手段 |
|---|---|---|
| **位置偏差** | 偏向先出现的那份回答 | pairwise 强制双向换位：两个顺序都判同一方赢才记胜，否则记平局 |
| **冗长偏差** | 篇幅越长分越高 | 评分表里写死"长度不构成加分理由" + 事后度量"更长一方获胜率" |
| **自偏好** | 给自己模型族的回答打高分 | 配置层校验裁判与 SUT 是否同族，同族直接告警 |
| **风格偏差** | 偏爱自信、排版漂亮的回答 | 评分表锚点约束 + 人工 gold set 校准兜底 |

### 位置交换为什么有效

每个配对各判两次（A 先 / B 先）。位置敏感的那部分噪声被转成**诚实的平局**，
而不是虚假的胜负。代价是多一次调用，收益是结论可用了。

### 态度

这些偏差**不可能被消除，只能被度量 + 缓解 + 如实披露**。
所以报告会把度量结果原样列出（位置一致率、冗长获胜率、同族告警），
而不是假装评测结果没有偏差。

**一个不肯公布自己裁判一致率的评测报告，它的分数没有意义。**

## 九、评估 SOP

组织一次评测的标准流程：

### 阶段一：定义（不写代码）

1. 明确**这次要回答什么问题** —— 是选型？是回归？还是定位短板？
   三个问题的评测集构成完全不同。
2. 确定能力维度范围，以及每个维度的判定方式。
3. 为每个维度写评分表（criterion + steps + anchors + output schema）。

### 阶段二：建集

1. 从真实失败、真实用户请求出发收集种子（Anthropic 的建议：20 条覆盖真实失败模式的样本，
   比 200 条只测 happy path 的合成样本更有价值）。
2. 每道题**只能测一件事**。
3. 有唯一答案的必须给 `reference`；无唯一答案的也必须给 `reference`（哪怕只是要点清单）。
4. 平衡测试集：**既测"该做时做了"，也测"不该做时没做"**。
   安全维度就是这个原则的直接体现（`should_refuse` 与 `should_answer` 两类都要有）。

### 阶段三：校准裁判

1. 抽 100-500 条，人工按同一张评分表打分。
2. 算加权 κ。**κ < 0.6 就回去改评分表或换裁判，别急着跑全量。**
3. 记录 κ 值，写进报告。

### 阶段四：跑评测

1. 先用 `--limit 20` 小规模试跑，确认配置和链路。
2. 全量跑，开启 `--pairwise`。
3. 检查错误率。**错误率异常时先修链路，再看能力结论** —— 把调用失败混进能力统计会污染结论。

### 阶段五：读结果与闭环

1. 看榜单：差距是否超过置信区间。
2. 看短板：哪个维度均分最低。
3. 看归因：失败类型分布是什么。
4. **把归因转成数据动作**，定向补样本，再评测一轮。
   这一步才是闭环的出口 —— 不出动作的评测报告，只是一份好看的文档。

## 十、数据飞轮闭环

```
    评测集 ──→ 推理 ──→ 三层判定 ──→ 归因分析
      ↑                                    │
      │                                    ↓
      └──── 定向补样本 ←──── 数据策略建议 ←─┘
```

`analysis.build_strategy()` 把失败类型映射成具体的数据动作：

| 失败类型 | 数据动作 |
|---|---|
| 指令约束违规 | 合成多约束组合样本：否定约束 + 格式约束 + 长度上限同时出现 |
| 事实性不足 | 补事实核验数据：同一问题给正例与常见错误说法，要求区分"材料支持"与"似是而非" |
| 工具使用不当 | 补工具轨迹数据，重点覆盖参数完整性（缺参应先追问）与工具选择歧义场景 |
| 安全边界失守 | 补提示注入与越权样本：把违规指令藏在文档、表格、工具返回值里 |
| 输出格式不合规 | 把结构化输出作为硬约束写进训练与评测 |
| 内容质量偏低 | 按失败子维度分别取样，先定位是哪一维拖后腿 |
| 未产出有效回答 | 先排查调用链路问题，这类不是能力问题，混进能力统计会污染结论 |

## 十一、多智能体与知识图谱：判定设计说明

### 11.1 多智能体：为什么几乎全用确定性判定

多智能体系统的失效模式都很具体、可枚举，也都可以在协作消息记录上直接数出来：

| 失效模式 | 判定方式 |
|---|---|
| 审查者从不否决 | 统计 reviewer 的 verdict 里有没有出现过 reject —— 从不说「不」的审查者等于不存在 |
| 否决了但没人改 | 检查否决之后是否出现第二轮 executor，且内容与上一轮不同（协作断链最常见的一环） |
| 某个角色包办所有消息 | 统计各角色消息占比，单一角色超过 80% 判为「独角戏」 |
| 该发现的问题没发现 | 题目预埋 `expected_reviewer_flag`，检查审查意见是否命中 |

这些都是可数的事实，不需要主观判断。裁判只在最后一层兜底「最终答案质量」。

**一个容易搞混的地方**：裁判要「独立打分、互不可见」，而被测的多智能体角色**必须共享上下文**。
两者目的正好相反 ——
裁判独立是为了消偏（互相可见就不再是独立样本）；
协作角色共享是为了完成任务（信息不流通就协作不起来）。
把这两件事混起来，两边都会做错。

### 11.2 知识图谱：方向错误必须单独报出来

三元组判定里，「A 属于 B」与「B 属于 A」实体都对、关系也对，只是方向反了。
如果笼统地报「错了一条」，就分不清这是方向问题还是实体识别问题 ——
而两者的修法完全不同。

所以在 `detail` 里单列 `reversed_direction` 字段。危害程度上也不一样：
实体错只是查不到，方向反了会让查询走到完全相反的方向上去，在下游是灾难性的。

### 11.3 两个维度的共同点

都体现同一条贯穿全项目的原则：**能用确定性方式判定的，绝不交给裁判。**

多智能体的四个失效模式、知识图谱的三元组对错，全都是可以精确判定的事实。
把这类判断交给 LLM，换来的是：更贵、更不稳、还引入原本不存在的偏差。
