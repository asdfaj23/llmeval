# 架构说明

这份文档回答：**代码是怎么组织的，以及要改一处东西应该动哪个文件。**

---

## 一、数据流

```
                    configs/models.yaml          configs/suites/*.yaml
                    （有哪些模型可用）            （跑哪些题、用哪些指标）
                            │                            │
                            └──────────┬─────────────────┘
                                       ↓
   datasets/*.jsonl  ──→  config.load_dataset()  ──→  [Sample, Sample, ...]
                                       │
                                       ↓  pipeline.Runner 展平成 Job 列表
                            Job(sample, spec, attempt_index)
                                       │
                                       ↓  run_parallel（线程池，concurrency 可配）
                     ┌─────────────────┴─────────────────┐
                     ↓                                   ↓
              sut.ChatSUT                        sut.AgentSUT
           （单轮对话，多数维度）            （两阶段工具调用，agent 维度）
                     │                                   │
                     └──────────┬────────────────────────┘
                                ↓
                        client.LLMClient.chat()
                    ┌───────────┴───────────┐
                    ↓                       ↓
            mock.MockEngine          真实 HTTP（urllib）
            （离线，确定性）      （重试/退避/缓存/成本统计）
                                │
                                ↓  Response（含 text 与 trace）
              ┌─────────────────┼─────────────────┐
              ↓                 ↓                 ↓
   metrics.deterministic   metrics.agent_metrics  metrics.judge
      Tier1 规则判定          Agent 轨迹指标        Tier2 LLM 裁判
              │                 │                 │
              └─────────────────┼─────────────────┘
                                ↓
                        Turn(sample, response, [Verdict, ...])
                                │
        ┌───────────────────────┼───────────────────────┐
        ↓                       ↓                       ↓
  pipeline._persist      analysis.summarize_model   bias.summarize_bias
  turns.jsonl            （聚合 + 归因 + 策略）      （偏差度量）
  summary.json                   │
  pairwise.json                  ↓
                          report.render_html  ──→  report.html
                          
                          calibration.run_calibration
                          （人工标注 → κ → 报告「裁判可信度」区块）
```

**一条记录 = 一个 `Turn`**，它同时带着：题面、原始回答、工具轨迹、每个判定的完整依据。
事后被质疑分数时，能一条条翻回去看。这是可追溯性的最低要求。

## 二、模块职责

| 文件 | 职责 | 不该做的事 |
|---|---|---|
| `schema.py` | 数据结构 + 能力维度表 + 确定性伪随机 | 不读文件、不发请求 |
| `config.py` | 读 YAML、解析 .env、校验模型可用性 | 不包含业务逻辑 |
| `client.py` | HTTP 调用、重试、缓存、并发调度 | 不知道"题目"是什么概念 |
| `mock.py` | 离线模拟引擎 | 只在 provider=mock 时被调用 |
| `sut/base.py` | SUT 抽象 + 题面渲染 | 不做判定 |
| `sut/chat_sut.py` | 单轮对话 | — |
| `sut/agent_sut.py` | 两阶段工具调用 + 轨迹采集 | 不评价轨迹好坏 |
| `sut/multi_agent_sut.py` | 三角色协作 + 协作消息采集 | 不评价协作好坏 |
| `sut/multi_turn_sut.py` | 多轮对话：逐轮发送、保留完整历史 | 不做判定；**绝不把 turns 拼成一条发送** |
| `sut/tools.py` | 工具集与安全算术（三个 SUT 共用） | 不知道自己在被谁调用 |
| `metrics/deterministic.py` | Tier1 规则判定 | 不调模型 |
| `metrics/judge.py` | Tier2 裁判（prompt 构建 + 解析 + 换位 + 评审团） | 不算统计量 |
| `metrics/agent_metrics.py` | Agent 指标 + pass@k / pass^k | 不调模型 |
| `metrics/collaboration.py` | 多智能体协作指标（全确定性） | 不调模型 |
| `metrics/kg_metrics.py` | 三元组 F1、多跳路径匹配（全确定性） | 不调模型 |
| `metrics/coding_exec.py` | 代码真实执行：子进程隔离 + 硬超时 + 静态黑名单 | 不调模型；但**不是强沙箱** |
| `metrics/multiturn.py` | 多轮三指标：最终答案 / 约束保持 / 纠错更新 | 不调模型 |
| `media.py` | 图片加载与 data URL 转换 | 只读文件 |
| `stats.py` | 配对显著性检验（McNemar + bootstrap 区间） | 纯统计，不调模型 |
| `bias.py` | 偏差度量 | 不修改数据 |
| `calibration.py` | κ / 一致率 / 自助法区间 | 不打分 |
| `pipeline.py` | 编排：展平任务 → 并发执行 → 汇总落盘 | 不做分析 |
| `analysis.py` | 聚合、归因、数据策略 | 不生成 HTML |
| `report.py` | 渲染 HTML / SVG | 不读原始数据文件（接收结构体） |
| `cli.py` | 命令行 | 不写业务逻辑 |

**分层的硬约束**：
- `metrics/*` 不导入 `pipeline`，`analysis` 不导入 `report`
- 依赖方向永远是单向的：`cli → pipeline → (sut, metrics, analysis) → (config, client, schema)`
- 这样任何一层都能单独测

## 三、关键数据结构

```python
Sample                     评测集里的一道题
├ id, dimension, task_type, difficulty
├ prompt, system, context
├ reference                参考答案（有 gold 才能做精确比对）
├ constraints              显式约束列表（交给 Tier1 判定）
└ meta                     expected_tools / forbidden_tools / answer_type / ...

Response                   某个模型对某道题的一次回答
├ text, error
├ trace                    Agent 工具调用轨迹 [{step, tool, args, result, ok}]
├ messages                 多智能体协作消息 [{turn, role, content, verdict, issues}]
├ usage                    token / 成本
├ attempt_index            第几次重复（用于 pass^k）
└ latency_s

Verdict                    某个指标对某次回答的判定
├ metric                   instruction_rules / answer_match / safety_heuristic
│                          / agent_tools / judge:faithfulness ...
├ tier                     deterministic | llm_judge | human
├ score                    统一归一到 1-5
├ passed                   是否通过
├ detail                   完整判定依据（可追溯的核心）
└ judge_id, usage, error

Turn = Sample + Response + [Verdict]     落盘的基本单位
```

`Verdict.detail` 是这套设计的关键。它保留了判定过程，
所以报告能展开「为什么这条是 1 分」，而不是只给一个数字。

## 四、怎么扩展

### 4.1 加一个新的能力维度

1. `src/llmeval/schema.py` 的 `DIMENSIONS` 里加条目，写好 `name` 和 `seed_anchor`
   （**必须写清对齐依据** —— 这是这张表存在的意义）
2. `datasets/` 下新建 JSONL，样本的 `dimension` 填新 key
3. 在 `configs/suites/*.yaml` 的 `per_dimension` 里指定用哪张评分表
4. 跑 `run.py list` 确认维度被识别

### 4.2 加一个新的判定指标

**确定性指标**：在 `metrics/deterministic.py` 里写函数，签名固定：

```python
def evaluate_xxx(sample: Sample, response: Response) -> Verdict | None:
    if 不适用:
        return None          # 返回 None 表示这一层不适用，不参与统计
    ...
    return Verdict(
        sample_id=sample.id, sut_id=response.sut_id,
        metric="xxx", tier="deterministic",
        score=1.0~5.0, passed=bool, detail={...},
        attempt_index=response.attempt_index,
    )
```

然后加进 `collect_deterministic()` 的元组里。

**裁判指标**：只需要写一张评分表 YAML（放 `configs/rubrics/`），
`judge.py` 会自动按 G-Eval 范式构建 prompt。
**不用改 Python 代码** —— 这是评分表设计成配置文件的意义。

### 4.3 加一种被测对象

继承 `BaseSUT`，实现一个方法：

```python
class RagSUT(BaseSUT):
    kind = "rag"
    def run(self, sample, attempt_index=0) -> Response:
        # 你的检索 + 生成逻辑
        return Response(sample_id=sample.id, sut_id=self.spec.id, text=answer, ...)
```

然后在 `sut/__init__.py` 的 `build_sut` 里注册，并在 `_KIND_BY_TASK` 里补上题型映射。
判定层、报告层、分析层**完全不需要改动**。

现成的三个例子可以照着抄，复杂度递增：

| SUT | 形态 | 额外采集什么 |
|---|---|---|
| `ChatSUT` | 最简，一问一答 | — |
| `AgentSUT` | 单智能体 + 工具调用 | `trace`：工具调用轨迹 |
| `MultiAgentSUT` | 三角色协作 | `messages`：协作消息记录 |

**如果新增的过程记录需要落盘**，记得同步 `schema.Response` 和 `pipeline.load_run`
的读取逻辑 —— 少改一边会导致「重跑结果对、读回来却是空的」这种很难查的问题。

### 4.4 加一个新的模型服务商

只改 `configs/models.yaml`：

```yaml
providers:
  my_provider:
    label: 某服务商
    base_url: https://api.example.com/v1
    api_key_env: MY_API_KEY
```

所有 provider 走 OpenAI 兼容协议。如果服务商的返回结构与标准不同，
才需要动 `client.LLMClient._parse_response`。

### 4.5 改评分标准

直接改 `configs/rubrics/*.yaml`。**改完必须重新校准** ——
评分表一变，之前算的 κ 就作废了。

## 五、成本与性能控制

| 手段 | 位置 | 效果 |
|---|---|---|
| **结果缓存** | `client._cache_key` | 相同 (provider, model, messages, 参数) 复用响应，重跑不花钱 |
| **裁判抽样** | `suite.judge_sample_ratio` | 生产设 0.1-0.2，成本降 5-10 倍 |
| **Tier1 优先** | `metrics/deterministic.py` | 能规则判的不用裁判，直接省掉调用 |
| **题量限制** | `--limit N` | 先小规模试跑 |
| **分层执行** | `run` / `report` 拆开 | 出报告不重新调模型 |
| **本地判定** | 全部统计 | 统计量纯 Python 实现，零额外计算成本 |

缓存默认开启（`outputs/.cache`），是**纯文本 JSON**，体积很小，
可以直接删掉重置。它是缓存不是数据，删了不影响任何已落盘的评测结果。

## 六、测试

```bash
python -m pytest tests -q
```

**所有测试都是离线的**，用 mock provider，不调任何真实 API，不依赖网络。
这是刻意的 —— 依赖外部服务的测试会变成"时好时坏"的东西，最后没人跑。

覆盖范围：

| 测试文件 | 覆盖内容 |
|---|---|
| `test_deterministic.py` | 全部约束类型 + mcq/数值比对 + 安全启发式 |
| `test_judge.py` | prompt 构建、JSON 解析降级、换位逻辑 |
| `test_calibration.py` | κ 计算、加权 κ、自助法区间、样本不足时的行为 |
| `test_agent_metrics.py` | 工具 F1、冗余步数、pass@k / pass^k |
| `test_collaboration.py` | 角色覆盖、独角戏检测、审查履职、修订闭环 |
| `test_kg_metrics.py` | 三元组抽取（5 种写法）、F1、方向错误、多跳路径 |
| `test_panel.py` | 评审团打分、裁判间一致性、中位数聚合抗离群 |
| `test_pipeline.py` | 端到端跑通、落盘、读回一致性 |

## 七、已知限制

诚实列出来，比假装没有强：

1. **评测集只有 74 题**，是流程验证用的种子集，不是生产题库。
2. **代码判定没有做真正的执行测试。** `coding` 维度目前靠裁判读代码打分，
   完全可以接一个沙箱执行器跑测试用例 —— 这是最值得做的下一步扩展。
3. **`repeats` 只在 agent 维度开了 3 次。** 其他维度跑 1 次，算不出 pass^k。
4. **没有 web 界面。** 报告是静态 HTML，`run` 是命令行。
   刻意保持这样：评测工具的价值在结果可信，不在交互好看。
5. **缓存只在磁盘，没有过期策略。** 换模型版本时建议手动清一次 `outputs/.cache`。
