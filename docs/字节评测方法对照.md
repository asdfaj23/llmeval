# 评测方法学对照：字节 Seed 与近两年顶会论文

这份文档回答一个问题：**这个项目里的每一条设计，依据是什么。**

写它有两个用途：一是自证不是拍脑袋搭的框架；二是面试时被问到「你这个评测集怎么建的」，
可以照着讲，每一句都有出处。

---

## 一、字节 Seed 的评测方法学

### 1.1 三原则（Seed1.8 Model Card 附录 A）

原文的核心表述是：*benchmark scores must serve as a reliable proxy for actual value*
（评测分数必须是真实价值的可靠代理）。三条原则：

| 原则 | 原文要点 | 本项目怎么落地 |
|---|---|---|
| **优先用户体验** | 先分析真实用户需求分布，再把用例映射成评测类别。Seed 用的是 ChatGPT 的用例分布作基线，信息检索、文本编辑、辅导是前三 | 见 1.4。题库配比按 Seed2.1 众测任务分布设计，办公类占最大权重 |
| **转向真实场景** | 从合成孤立任务，转向按「经济价值领域」组织的真实任务 | `realworld`（25 题）与 `office`（19 题）两个维度就属于这一层；`docs/评测体系.md` 里每个维度都标了 seed_anchor |
| **推进智能前沿** | 另设高阶推理/数学/代码评测，测峰值能力而非平均能力 | `reasoning` 40 题、`coding` 30 题（全部真实执行测试） |

### 1.2 产品驱动评测法（Seed2.1 Model Card）

原文列了三条做法，逐条对应：

1. **dogfooding + 外部受邀测试 + 众测开发者持续迭代**
   → 本项目对应的是 `repeats` 机制与多轮维度：同一道题跑多次，看结果是否稳定
   （`analysis.py` 的 `reliability_table`，pass@k / pass^k）

2. **从用户返回的真实 bad case 持续扩展 benchmark；访谈企业用户与领域专家，把未满足需求转成评测任务**
   → 对应 `scripts/from_badcase.py`（数据飞轮）：从失败样本自动生成候选新题，
   人工确认后进题库。这条链路把「评测→失败分析→题库扩充」闭成了环

3. **用模型自己参与评测构建、失败分析、数据清洗**
   → 对应裁判评审团（`metrics/judge.py: evaluate_panel`）与自动化归因
   （`analysis.py: build_strategy`）。**注意边界**：模型可以辅助分析，但
   「报告里的判断题是谁出的」这件事必须在文档里说清楚，不能含糊

### 1.3 两个可直接借鉴的 benchmark 设计

**MM-BrowseComp 的 verified checklist**
> 每个问题配一份经过验证的检查清单，用于细粒度分析推理路径，区分「真推理」和「随机蒙对」。

本项目的对应实现：`Sample.meta` 里的 `key_facts` / `retention_checks` / `gold_triples` /
`gold_path`。它们不是参考答案的装饰，而是**判定时逐条核验的清单**，
落在 `metrics/multiturn.py`、`metrics/kg_metrics.py` 里。

**AInstein-SWE-Bench 的 fail-to-pass 容器化测试**
> 从真实科研仓库抽取任务，配 test-driven 的 fail-to-pass 判定，在容器环境内执行。

本项目对应 `metrics/coding_exec.py`：把模型代码放进独立子进程，用预置测试用例跑，
全过才算通过（与 HumanEval 的 pass@1 口径一致）。

**必须说清的差距**：Seed 用的是真容器与真实仓库快照；本项目是**子进程隔离 + 超时 + 静态黑名单**，
不是强沙箱。它足以应付自家模型产出的代码，但不适合执行来源不可信的任意代码。
这个区别不掩饰。

## 二、近两年顶会论文的方法

### 2.1 NeurIPS 2025《Measuring what Matters: Construct Validity in LLM Benchmarks》

这是最该读的一篇。作者系统审阅了 **445 篇 benchmark 论文**（ICML/ICLR/NeurIPS 2018-2024，
ACL/NAACL/EMNLP 2020-2024），29 位专家逐篇编码，得出的关键数字：

| 发现 | 比例 |
|---|---|
| 没有定义所测现象 | 21.7% |
| 使用了「有争议」的概念定义 | 47.8% |
| 便利抽样（复用现成数据集） | 39.2% |
| **比较模型时用了统计检验或不确定度估计** | **仅 16.0%** |
| 报告了单点准确率但无置信区间 | 绝大多数 |

八条建议，以及本项目的落实情况（诚实标注）：

| # | 建议 | 本项目 | 状态 |
|---|---|---|---|
| 1 | 定义所测现象 | `schema.py: DIMENSIONS` 每个维度都有 name + seed_anchor | ✅ |
| 2 | 只测该现象 | 每个维度配独立 rubric，判定分层 | ✅ |
| 3 | 构建有代表性的数据集 | 368 题按真实用例分布设计 | ⚠️ 部分 |
| 4 | 承认复用数据集的局限 | 本题库全部自建，未复用公开数据集 | ✅ |
| 5 | 防污染 | 题目自建且未公开，污染风险低 | ⚠️ 无法完全排除 |
| 6 | 用统计方法比较模型 | `stats.py`：McNemar + bootstrap 配对检验 | ✅ |
| 7 | 做错误分析 | `run.py failures` + 报告失败明细 + 短板归因 | ✅ |
| 8 | 论证构念效度 | 本文档 | ✅ |

三条要诚实说明的地方：

- **第 3 条只有部分成立。** 368 题是人工构造的，不是从真实用户请求里采样的。
  Arena-Hard 的 BenchBuilder 是用真实查询做种子，本项目的 `scripts/build_eval_set.py`
  实现了那套质量打分与分层取样，但输入仍是自建题。这是与 Seed 方法最主要的差距。
- **第 5 条无法完全保证。** 自建题目降低了污染概率，但无法证明模型没见过类似题目。
  可行做法是保留一部分「冷题库」（建好后不公开、不进任何文档），定期用冷题库复测。
- **第 6 条是这次改动最大的收获。** 之前报告只报分数和 bootstrap 区间，
  但两个模型的**配对差异**没有做检验，等于把「分高就是强」当成了默认前提。

### 2.2 ICLR 2026《Foundational Automatic Evaluators》(FARE)

这篇讲的是把评测本身当成一个任务来训练。可借鉴的是它归纳的**五类评测任务**：

| 任务类型 | 本项目对应 |
|---|---|
| pairwise comparison | `metrics/judge.py: evaluate_pairwise`（带位置交换） |
| step-level evaluation | `metrics/collaboration.py`（多智能体逐轮核验）、`metrics/multiturn.py` 的分轮判定 |
| reference-based verification | `evaluate_answer`、`kg_metrics.evaluate_triples` |
| reference-free verification | `rubric` 里的事实忠实度判据 |
| single rating | `evaluate_pointwise`（G-Eval 形态） |

另一个有意思的发现是**位置偏差会随评测数据规模自然缓解**，这与本项目
`bias.py` 里「换位对比 + 只在两个顺序都判同一方赢时才计胜」的做法是互补的两条路。

### 2.3 ICLR 2026《DEEPSYNTH》

120 个任务、7 个领域、67 个国家，SOTA 模型在其上只拿到 F1 8.97 / judge 17.5。
它的构建流水线值得抄：

> 标注者收集官方数据源 → 提出假设 → 人工分析 → 设计带**可验证答案**的任务

本项目题库的构建遵循同样顺序：先定可验证的判定口径（tests / key_facts / gold_triples），
再写题目，而不是先写题再想怎么判。

### 2.4《LLMs Get Lost in Multi-Turn Conversation》

把一条完整指令拆成多轮逐步给出，模型表现平均下滑 **39%**。两个失效模式：

1. **过早作答**：信息未给全就先回答，后续新信息来了不修正
2. **遗忘前文**：早轮给出的约束到最后一轮已经丢掉

这两点直接构成了 `multiturn` 维度的三个确定性指标：

| 指标 | 对应哪个失效模式 | 实现 |
|---|---|---|
| `mt_final_answer` | 综合完成度 | 末轮答案与 gold 比对 |
| `mt_retention` | 遗忘前文 | 早轮约束在末轮是否仍被遵守 |
| `mt_correction` | 过早作答 | 中途更正的信息是否被采纳 |

题库里 24 道多轮题中，6 道埋了信息更正（`mt-009` ~ `mt-014`），
3 道埋了无关干扰（`mt-021` ~ `mt-023`）。

论文还指出第三个损失是**可靠性下降**（多次运行结果发散）。这个指标需要 `repeats > 1`，
在 `configs/suites/all.yaml` 里把 `multiturn.repeats` 调成 3 即可算出。

## 四、面试时怎么讲这套东西

一句话版本：

> 我做了一套大模型能力评测框架，方法学对齐字节 Seed 的三原则与产品驱动评测法，
> 题库 368 题覆盖 13 个维度、按 Seed 的众测任务分布配比；判定分三层——
> 能用程序算的绝不问模型，代码题真实执行测试，多轮题按《LLMs Get Lost in
> Multi-Turn Conversation》的两个失效模式设计；最后对比模型时做配对显著性检验，
> 而不是只报分差。

如果被追问「你怎么知道你的评测集是有效的」，答紧扣 NeurIPS 那八条，
并**主动说出哪几条没做到**（真实采样、防污染）——主动暴露局限比假装完备更可信。

如果被问「为什么有些题不用 LLM 判」，答：字数、禁用词、数值、工具序列这些有唯一答案，
用裁判判既贵又引入抖动，属于把确定性问题上交给随机过程。
