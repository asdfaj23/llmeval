# 沙盒与隔离

## 一、结论先行

**本项目做的是「弱隔离」，不是容器级沙箱。**

没有 Docker、没有 seccomp、没有系统调用过滤、没有强制断网。
它解决的是**「防污染 + 可复现」**这一层，不解决「防黑客逃逸」。

这么定位不是能力不够，而是**成本和收益的匹配问题**：
本项目所有工具都是纯函数——只读 `sample.context`，不写盘、不联网。
沙盒里其实没有东西可隔离。真正需要容器的是「把模型产出的代码丢进真实环境跑」
那一类任务，那条路径见 `metrics/coding_exec.py` 的子进程弱隔离。

---

## 二、为什么必须做隔离

评测有一个**静默失效**模式：答案就在模型眼前，它照抄一遍拿了满分，
而报告上只会显示「这个模型真强」。它不报错、不崩溃，只是让整轮评测变成废纸。

需要防的是四类风险：

| 风险 | 具体表现 | 后果 |
|---|---|---|
| 评测污染 | 模型通过文件或网络读到标准答案；或出题人把答案写进了题面 | 分数虚高，评测失效 |
| Benchmark 记忆 | 题目是公开的，模型训练时见过 | 测的是背题，不是能力 |
| Reward hacking | 模型察觉自己在被评测，开始伪装或钻规则空子 | 指标失真 |
| 工具越权 | 调了危险工具、把数据往外发 | 安全与合规问题 |

---

## 三、做了什么

代码在 `src/llmeval/containment.py`，三项审计全部**确定性、零 API 成本**：

### 3.1 答案隔离自检

受保护内容（`reference`、`meta.rationale`、`gold_triples`、`gold_path`、
`key_facts`、`expected_tools`、`tests` 里的 `expected`）**绝不能出现在
模型可见材料**（`system` + `prompt` + `context` + `turns`）里。

几个刻意的设计：

- **比对字符串叶子，不比对整个 JSON**。`tests` 里真正敏感的是每个 `expected`，
  而不是外层的括号和字段名。只比对整串会漏判。
- **短于 12 字的片段不参与比对**。选择题 gold「B」出现在材料里是正常的，
  把它当泄漏只会制造假警报——而一个总在误报的检查，最后没人会看它。
- **去掉所有空白再比对**，避免「换行位置不同」造成的漏判。

### 3.2 canary 泄漏扫描

每道题生成一个**确定性的**标记（`CANARY-` + 12 位十六进制，由 sample id 的
sha256 派生）。确定性是必须的：评测要可复现，同一个 sample 每次跑出的标记
必须一致，否则离线重放时对不上账。

模型输出或工具轨迹里一旦出现标记，就说明它读到了本该够不到的东西。
扫描的是**任意**标记而不只是本人那道题的——出现别的题的标记，
说明它越界读到了别处的内容，那是更严重的情况。

### 3.3 工具轨迹审计

轨迹已经全量落盘，所以越界行为一定留痕，不需要事中拦截也能事后复盘。
检查两类：

- **未授权工具**：调用了白名单（`search_corpus` / `calculator` / `get_field` / `finish`）之外的工具。
- **可疑参数**：路径穿越（`../`）、系统目录（`/etc`、`/proc`）、
  答案文件名（`gold.json`、`answer.txt`）、外网地址、系统或网络命令。

可疑参数的黑名单**刻意收窄**：像 `format`、`del` 这类词在正常技术提问里太常见，
放进来只会把「问了一个格式化问题」误报成越界。

### 3.4 实测结果

在 368 道真实题目上跑全库自检：

```
$ python scripts/audit_isolation.py
扫描样本        : 368
受保护片段      : 337（长度 >= 12 字的参考答案 / 金标 / 测试期望值）
发现泄漏        : 0
结论：没有参考答案或金标内容出现在模型可见材料里。
```

这条检查同时进了 CI（`--fail-on-leak`），以后再出题时，
只要有人把答案顺手写进题面，CI 会直接拦下来。

## 四、还没有做什么

坦白列出来，比假装没有强：

- 没有**容器级沙盒 / 镜像**（没有 Docker、没有 seccomp）。
- 没有**强制断网**：调真实 API 时是走网络的。
- 没有把**答案与评测环境物理隔开**：题库和答案目前就是普通文件，
  靠的是「工具只读 context」这个设计约束，而不是文件系统权限。
- 没有**事中拦截**：只有事后审计。

## 五、该怎么做：八层防护，按成本从低到高

| # | 措施 | 挡住什么 | 成本 |
|---|---|---|---|
| 1 | 答案与评测环境**物理隔离**（受保护内容放在被测进程读不到的路径） | 偷看答案 | 零成本 |
| 2 | **工具白名单 + 入参校验**（已有） | 工具越权 | 零成本 |
| 3 | **每题一个独立临时目录**，素材只读挂载，跑完即删 | 串题、残留 | 零成本 |
| 4 | **默认断网** | 联网搜题、数据外泄 | 零成本 |
| 5 | **超时 / 内存 / 步数上限**（已有） | 死循环、刷步数 | 零成本 |
| 6 | **canary 泄漏检测**（已有） | 偷看答案 | 零成本 |
| 7 | **轨迹审计**（已有） | 越狱行为 | 零成本 |
| 8 | **容器 / 微 VM 强隔离**（Docker + seccomp + 只读根 + 无网络） | 真正的逃逸 | 高成本 |

**优先级就是 1 → 7。** 前七条全是纯代码、零 API 成本，
就能拦住绝大多数「越狱读答案」。第八条留到真要在真实环境跑智能体的时候再上——
它的成本和运维量跟现阶段不成比例。

## 六、一个设计决定：隔离结论为什么不计入质量分

`containment` 判定的 `decisive=False`，也就是说：

- 它出现在报告和 `summary.json` 里，**如实披露**；
- 但它**不会抬高或拉低任何模型的能力分**。

理由：越界是**「这轮结果还能不能用」**的问题，不是**「模型好不好」**的问题。
把隔离问题和能力分混在一起平均，只会让「环境有问题」被稀释成一个
看不出所以然的分数变化——真正该做的动作（这一轮作废重跑）反而被掩盖了。

这与报告里另外两条硬性披露是同一个原则：用了 mock 必须挂红条，
κ 未达 0.6 必须标「仅供参考」——**环境层面的问题，用环境层面的方式披露，
不要混进能力分里**。

## 七、怎么跑

```bash
# 全库答案隔离自检（零成本，全离线）
python scripts/audit_isolation.py

# 有泄漏就返回非零退出码，给 CI 用
python scripts/audit_isolation.py --fail-on-leak
```

运行评测时，隔离审计会自动挂在会调用工具的题型上
（`agent_tool` / `multi_agent` / `coding`），结果写进
`summary.json` 的 `containment` 字段，并在 HTML 报告的
「评测环境隔离」一节里披露。
