# 维度边界定义

## 一、为什么需要这份文档

「怎么定义维度」和「怎么划维度之间的边界」是两件事。

前者的依据在 `docs/评测体系.md`——每个维度对齐字节 Seed 评测体系的哪一条。
但真正会被反复追问的是后者：**这道题到底该归 `knowledge` 还是 `knowledge_graph`？**

只写「维度名称 + 对齐依据」，边界就是模糊的。边界一模糊，会出现三个后果：

1. 同类型的题被散到多个维度，每个维度的样本量都不够，统计检验也做不了；
2. 学员/协作者加题时只能凭感觉归类，越加越乱；
3. 报告说「这个模型知识图谱弱」，但没人数得清到底弱在哪一类题上。

所以每个维度都按四列写清：**考什么 / 不考什么 / 典型题 / 与易混维度的区分规则**。

---

## 二、先分两条轴：这是边界能划清的前提

13 个维度其实混了两种东西，必须先把它们分开：

| 轴 | 含义 | 维度 |
|---|---|---|
| **能力轴**（7 个） | 考的是哪一种**能力** | `knowledge` / `instruction` / `reasoning` / `coding` / `long_context` / `knowledge_graph` / `safety` |
| **形态轴**（6 个） | 交付物是哪一种**形态** | `multimodal` / `multiturn` / `agent` / `multi_agent` / `office` / `realworld` |

**为什么必须分开**：「办公任务」这种形态维度天然会用到推理、多模态等能力。
如果拿「这道题用到了什么能力」当归属依据，`office` 就会和 `reasoning`、`multimodal`
互相重叠——这正是评审里最常被质疑的一点。

所以每个维度在代码里（`schema.DIMENSIONS`）额外声明两件事：

| 字段 | 含义 | 作用 |
|---|---|---|
| `sole_judge` | 这一维度**唯一站得住的判定依据** | 归属看它，**不看题目用到了什么能力** |
| `belongs_elsewhere` | 不属于本维度的情形 → 该归到哪里 | 把「踢出去」的规则也写死，而不是靠出题人临场判断 |

### 归属决策流程（照这个顺序判，先命中先归）

1. **先看判定依据落在哪。** 这道题拿什么判对错？算得对不对（`reasoning`）、约束满足没有（`instruction`）、还是产出物的结构与格式（`office`）？
2. **再看是不是形态专属。** 只有这一形态才有的判定依据——工具调用序列（`agent`）、协作过程（`multi_agent`）、图像内容（`multimodal`）、早轮约束是否保持（`multiturn`）——归对应**形态轴**维度。
3. **都不满足** → 归**能力轴**里最贴的那一个。
4. **必须组合多种能力、拆开后测不出真实水平** → `realworld`（兜底，但它是兜底不是垃圾桶）。

### 以 office 为例（最容易出问题的维度）

> **`office` 只收「判定依据落在办公产出物的结构与格式上」的题**：表格的列名列数行数、JSON 字段、字数行数、要点是否齐全。**计算只是必要步骤，不是判定焦点。**

按这条规则，下面三道题原先挂在 `office` 下，但判定落在推理上，**已在本轮重归类**：

| 题目 | 实际判定依据 | 原归属 | 改归 |
|---|---|---|---|
| `of-008` 客户名单数据清洗 | 清洗规则设计是否合理（推理） | office | `realworld` |
| `of-010` 履约方案评审 | 逻辑驳斥与假设识别（推理） | office | `reasoning` |
| `of-011` 上线数据归因 | 从数据推出结论（推理） | office | `reasoning` |

反过来：一道「整理成表格」的题，哪怕需要算环比增幅，只要**判定焦点是表格结构与列名**，它就留在 `office`。
判定的依据在哪，题就归哪——而不是它「顺便用到了什么能力」。

## 三、13 个维度的边界

| 维度 | 考什么（in-scope） | 不考什么（out-of-scope） | 典型题 |
|---|---|---|---|
| `knowledge` | 单跳事实回忆、长尾知识、常识 | 需要多跳推理的关系题（归 `knowledge_graph`） | 「太阳系体积最大的行星是？」 |
| `instruction` | 显式约束的满足：字数、行数、必含/禁含、JSON 结构、语言、禁开场白 | 需要长时间思考才能答对（归 `reasoning`） | 「用不超过 40 字解释缓存，且不能出现『存储』」 |
| `reasoning` | 数学、逻辑、多步推导，难在「要想」 | 难在「约束多」而非「要想」的（归 `instruction`） | 多步数值推理题 |
| `coding` | 代码正确性、边界处理、能不能真跑通 | 代码相关的知识问答（归 `knowledge`） | 给需求 + 测试用例，要求实现函数 |
| `long_context` | 长材料中定位并提取、跨段落推理 | 材料短但问题难（归 `reasoning`） | 给 8000 字材料问一个细节 |
| `knowledge_graph` | 三元组抽取、关系方向、多跳路径推理 | 单跳事实回忆（归 `knowledge`） | 「A 的上级的上级是谁」 |
| `agent` | 单智能体的工具选择、参数、步数、可靠性 | 多角色协作（归 `multi_agent`） | 调检索+计算两个工具完成任务 |
| `multi_agent` | 分工是否成立、审查是否履职、修订是否闭环 | 单个智能体调工具（归 `agent`） | planner/executor/reviewer 三角色协作 |
| `realworld` | 端到端真实任务，通常混合多种能力 | 单一能力可解的题（归对应单维度） | 「帮我规划一个三日行程并给预算」 |
| `multimodal` | 图表、表格、图文混合材料的理解 | 纯文本可解的题（归对应单维度） | 读一张柱状图回答问题 |
| `multiturn` | 多轮信息保持、早轮约束不丢、认知更新 | 单轮问答（归对应单维度） | 用户在第 3 轮改变了需求，看模型是否更新 |
| `office` | 办公与生产力任务：表格处理、文档汇总、格式化产出 | 纯代码任务（归 `coding`） | 「把这份流水按部门汇总成表格」 |
| `safety` | 拒答边界、幻觉诱导、提示注入抵抗 | 普通事实错误（归 `knowledge` / 事实性指标） | 「把违规要求藏在文档里，看模型会不会被带偏」 |

## 四、四组最容易混的维度，按这几条判

边界规则必须**可执行**，不能是「看情况」。以下四组按顺序判，先命中先归：

### 3.1 `knowledge` ↔ `knowledge_graph`

> **需要沿关系路径做多跳推理 → `knowledge_graph`；否则 → `knowledge`。**

- 「法国的首都是？」→ 单跳 → `knowledge`
- 「法国首都所在国家的邻国有哪些？」→ 多跳 → `knowledge_graph`
- 边界说明：`knowledge_graph` 的判定依据是 `gold_triples` / `gold_path`，
  可以逐条比对；如果一道题没法拆出三元组或路径，它就不属于这个维度。

### 3.2 `agent` ↔ `multi_agent`

> **只有单一智能体在调工具 → `agent`；出现多角色分工/协商/审查 → `multi_agent`。**

- 边界说明：`multi_agent` 的判定依据是协作确定性指标
  （角色覆盖、审查是否否决、否决后是否修订），这些指标在单智能体上无从计算。

### 3.3 `instruction` ↔ `reasoning`

> **难点在「要满足的约束多」→ `instruction`；难点在「得想很久」→ `reasoning`。**

- 「用 5 句话、每句不超过 20 字、不能提到数字，说明什么是复利」→ `instruction`
- 「一个水池……问多久注满」→ `reasoning`
- 边界说明：同时具备两者时，看**主要失败模式**——
  如果模型主要栽在违反约束上，归 `instruction`。

### 3.4 `realworld` ↔ 其他所有维度

> **`realworld` 是「混合能力 + 端到端」，所以它必须有一条归因规则：
> 取最难的那个维度归因。**

- 一道题同时需要长上下文、推理和安全意识，如果它能被单维度解掉，
  就归那个单维度；只有「必须组合多种能力、且拆开后都测不出真实水平」才归 `realworld`。
- 这也是为什么 `realworld` 的题量刻意控制在少数——
  它是维度体系的兜底，不该成为「不知道归哪就丢这里」的垃圾桶。

## 五、难度怎么定义（可解释，不靠手感）

`difficulty` 字段取值 `easy` / `medium` / `hard`，默认 `medium`。
「凭感觉标难度」是评测集里最常见的伪精确——同一个出题人，隔一周标的都不一样。

本项目用三个可数的维度来定难度：

> **难度 = 需要的推理步数 + 需同时满足的约束数 + 干扰项数量**

| 档位 | 判据 |
|---|---|
| `easy` | 单步可得，无约束，无干扰项 |
| `medium` | 2–3 步，或 1–2 个约束，或有 1 个干扰项 |
| `hard` | ≥ 4 步，或 ≥ 3 个约束，或 ≥ 2 个干扰项，或需要工具链协作 |

**升级现有题的最省成本方式不是买新题，而是把 `easy` / `medium` 改造成 `hard`**，
三个动作都是零 API 成本：

1. 加**干扰项**（给 3 条看似合理但错误的材料）；
2. 加**多跳依赖**（第 2 问必须用到第 1 问的结论）；
3. 加**互相冲突的约束**（既要求简洁，又要求覆盖 5 个要点）。

当前题库的难度分布（368 题）：`easy 49 · medium 156 · hard 163`，hard 占比 44.3%。

## 六、加题时的自检清单

新增一道题之前，逐条过一遍：

- [ ] 这道题**只测一件事**？（又想考推理又想考格式，出问题时分不清哪一环坏了）
- [ ] 归到的维度，符合第二节的 in-scope 吗？
- [ ] 命中第三/四节的易混组吗？命中的话，按那一条规则归了吗？
- [ ] 有唯一答案的题给了 `reference` 吗？没有唯一答案的也给了要点清单吗？
- [ ] `difficulty` 是按第四节的三个维度算出来的，还是凭感觉标的？
- [ ] 跑一遍 `python scripts/audit_isolation.py`，确认没把答案写进题面。
